1. What is kubefriend? — The Problem It Solves

Debugging a failing Kubernetes pod typically requires a developer to run 4–6 commands, read and correlate their outputs, and then reason about what went wrong:

kubectl get pod openrag-backend -n prod
kubectl describe pod openrag-backend -n prod
kubectl logs openrag-backend -n prod --previous
kubectl get events -n prod --field-selector involvedObject.name=openrag-backend

This is mechanical, repetitive, and requires K8s expertise. kubefriend replaces this entire workflow with a single natural-language question:

💬 "Why is my openrag-backend pod failing?"

The assistant automatically calls the right tools, reads the data, correlates it, identifies the root cause, and streams back a structured explanation with exact kubectl remediation commands.

Who it's for

  • Developers who own services but aren't Kubernetes experts
  • Platform engineers who want faster incident triage
  • SREs doing on-call — check dashboard, ask AI, fix fast
  • IBM Cloud / ROKS teams — includes CRD support for watsonx workloads, OpenSearch, Milvus, Presto

Key design decisions

DecisionRationale
Backend runs natively on Mac (no Docker)oc login tunnels to localhost — Docker containers can't reach these tunnels. Native process avoids the networking problem entirely.
SSE (Server-Sent Events) for streamingTokens stream to the browser as they're generated — no waiting for the full answer. Users see the agent "thinking" in real time.
LLM initialised lazilywatsonx validates credentials against IBM Cloud at init time. Lazy init means the server starts and serves health/dashboard even if LLM credentials are temporarily broken.
Kubeconfig from ~/.kube/configNo re-implementation of auth — reuses whatever kubectl already uses. Switching clusters = kubectl config use-context.

4. The Agent Reasoning Loop (ReAct)

ReAct = Reasoning + Acting. The agent alternates between thinking (LLM) and acting (tool calls) in a loop until it has enough information to answer.

User question ↓ Agent node — LLM reads question + system prompt + previous tool results ↓ Does the LLM want to call a tool? ├── YES → Tools node — executes the tool, appends ToolMessage to state │ ↓ │ back to Agent node (loop) │ └── NO → Stream final answer to browser → END

How the graph is wired (graph.py)

# Two nodes
builder.add_node("agent", agent_node)   # LLM thinks
builder.add_node("tools", ToolNode(TOOLS)) # executes tool calls

# Routing: after agent runs, check if it made a tool call
builder.add_conditional_edges("agent", should_continue)
# "tools" → always return to agent
builder.add_edge("tools", "agent")

State — what gets passed between nodes

AgentState = TypedDict with:
  messages: list  # full conversation history — grows with every node
                  # HumanMessage → AIMessage(tool_calls) → ToolMessage → AIMessage(text)

System prompt tells the LLM its rules

  • Investigate before answering — always call at least one tool
  • Call tools one at a time, in logical order (status → logs → events → deployment → PVC)
  • Structure the final answer: Observation → Root Cause → Remediation → Prevention
  • Include exact kubectl commands in remediation
  • Ask for namespace when not provided (except CRD queries — search all namespaces)

5. The 7 Kubernetes Tools

Each tool is a Python function decorated with @tool. LangChain reads the docstring to build the description the LLM uses to decide when and how to call it.

ToolWhat it fetchesWhen the agent uses it
get_pod_status Phase, container states, restart count, last termination reason (OOMKilled, Error), pod conditions First tool called for any pod question — establishes the baseline state
get_pod_logs Last N lines of container stdout/stderr (default 100) After seeing CrashLoopBackOff or high restarts — logs reveal the application error
get_pod_events Kubernetes events for a pod: scheduling failures, image pull errors, BackOff warnings When pod is Pending or status is unclear — events show the scheduler's reasoning
get_deployment Replica counts (desired/ready/available), rollout conditions, image versions, strategy When the user asks about a deployment, or when pod problem may be deployment-level
get_pvc PVC names, status (Bound/Pending/Lost), capacity, storage class, bound PV When a pod is stuck Pending — may be waiting for a PVC to bind
find_unused_pods Evicted, Succeeded, Failed, Unknown pods; long-running zero-restart pods Cleanup queries: "what pods are safe to delete?"
get_crd_resources Any Custom Resource Definition — auto-discovers group/version, supports filter by type/state/name/namespace IBM watsonx workloads, OpenSearch clusters, Milvus, Presto, Kafka, or any CRD in the cluster
How tool discovery works (get_crd_resources): Rather than hard-coding IBM-specific CRD group names, the tool calls the Kubernetes ApiextensionsV1Api to scan all CRDs and match by plural/singular/kind name. This makes it generic — it works for any CRD in any cluster automatically.

How to add a new tool

  1. Create backend/app/tools/my_tool.py with a @tool-decorated function
  2. Write a clear docstring — this is what the LLM reads to decide when to call it
  3. Add it to TOOLS list in backend/app/tools/registry.py
  4. Restart the backend — the agent picks it up automatically, no other changes needed

7. How watsonx Was Debugged & Made to Work

This section is a case study in diagnosing a real cloud integration issue.

The error

403 project_id 4be90509-... is not associated with a WML instance

Root cause

A watsonx project exists in IBM Cloud, but it had no Watson Machine Learning (WML) service instance associated with it. The LLM API requires a project to be linked to a WML instance — otherwise it can't run model inference.

Fix applied in IBM Cloud console

  1. Open dataplatform.cloud.ibm.com → select the project
  2. Go to Manage → Services & integrations
  3. Click Associate service → select or create a Watson Machine Learning instance

How we verified the fix

# Test before touching any code — probe the same API ChatWatsonx calls internally
client = APIClient(credentials=Credentials(url=..., api_key=...), project_id=...)
specs = client.foundation_models.get_model_specs()
# Result: OK — 17 models available  ← WML now working

How we found the right model

The model configured in .env (ibm/granite-3-8b-instruct) was not provisioned on this WML instance. We listed all available models and selected based on:

  • Instruction-tuned — base models can't follow "call this tool" instructions
  • Tool / function calling support — must return structured tool_calls JSON
  • Strong reasoning — multi-hop K8s diagnosis needs good chain-of-thought

Selected: meta-llama/llama-3-3-70b-instruct — best available model on the instance, full tool-calling support, proven in LangGraph agents.

Resilience fix added to the codebase

The original code built the LLM at module import time — if credentials fail, the server crashes on startup. We changed it to lazy initialisation: the LLM is only built on the first chat request. Health checks and the dashboard stay available even if LLM credentials are broken.

8. The Frontend — Chat & Live Dashboard

Chat Tab

  • Text input → POST to /api/chat → SSE stream
  • SSE events: token (stream text), tool_call (tool started), tool_result (tool returned), done, error
  • Tool Call Panel (right sidebar) — shows every tool call and its raw result in real time so users can see exactly what the agent investigated
  • Multi-turn conversation — history stored in memory per conversation_id

Dashboard Tab

  • Polls GET /api/dashboard?namespace=X every 30 seconds
  • Summary bar: Total / Running / Warning / Critical pod counts
  • Pod table: name, status badge, restarts, age, node, AI diagnosis, suggestion, "Ask AI" button
  • Namespace selector — dropdown of all namespaces in the cluster
  • "Ask AI" pre-fills the chat tab with the pod name for one-click deep diagnosis

SSE hook (useChat.ts)

// Browser opens a persistent HTTP connection
const source = new EventSource("/api/chat", ...)
source.onmessage = (e) => {
  const event = JSON.parse(e.data)
  if (event.type === "token")       appendToken(event.data)
  if (event.type === "tool_call")   showToolCall(event.data)
  if (event.type === "done")        setComplete()
}

9. Multi-Cluster Support

kubefriend reads ~/.kube/config — the same file kubectl uses. Switching clusters requires no code changes:

# See all available clusters
./kubefriend contexts

# Switch to local Rancher Desktop
./kubefriend switch rancher-desktop

# Switch to IBM ROKS (requires oc login tunnel first)
./kubefriend switch lh-wxd-dev-us-south-db-roks24-oc

# Switch to AWS EKS
./kubefriend switch arn:aws:eks:us-east-1:123:cluster/my-eks

The kubefriend switch command runs kubectl config use-context <name> and restarts the backend process automatically.

ROKS / OpenShift note: oc login creates a tunnel to the cluster API on localhost:PORT on your Mac. The backend reads this directly from kubeconfig — no special handling needed when running natively.

11. Running & Operating kubefriend

First-time setup

git clone https://github.com/sijics/kube-friend
cd kube-friend
./install.sh            # creates venv, installs deps, builds frontend
cp .env.example .env    # fill in your API keys

Start / stop

./kubefriend start      # backend on :8000, frontend on :5173
./kubefriend stop       # kill both processes
./kubefriend restart    # stop + start
./kubefriend status     # show running PIDs + health check
./kubefriend logs       # tail backend log

LLM switching

./kubefriend llm openai     # switch to GPT-4o
./kubefriend llm watsonx    # switch to IBM watsonx (LLaMA 3.3 70B)
./kubefriend llm ollama     # switch to local Ollama

Cluster switching

./kubefriend contexts                     # list all kubeconfig contexts
./kubefriend switch rancher-desktop       # local cluster
./kubefriend switch my-roks-context       # ROKS (run oc login first)

12. End-to-End Walkthrough: "Why is my pod crashing?"

This is exactly what happened when tested live against the demo-crashloop pod in the kubefriend-test namespace using watsonx (LLaMA 3.3 70B).

User question: "Why is my demo-crashloop pod failing in the kubefriend-test namespace?"

Step 1 — Agent calls get_pod_status

Tool: get_pod_status(namespace="kubefriend-test", pod_name="demo-crashloop")

Result:
  Phase     : Running
  Restarts  : 317
  State     : Waiting — CrashLoopBackOff
  LastState : Error (exit=1) at 2026-08-17 13:39:55

Step 2 — Agent calls get_pod_logs (sees exit=1, needs app error)

Tool: get_pod_logs(namespace="kubefriend-test", pod_name="demo-crashloop", tail_lines="100")

Result:
  2026-08-17T13:39:53Z starting       # container printed "starting" then immediately exited

Step 3 — Agent calls get_pod_events (confirms pattern)

Tool: get_pod_events(namespace="kubefriend-test", pod_name="demo-crashloop")

Result:
  ⚠ BackOff (x4836) — Back-off restarting failed container app

Step 4 — Agent streams final answer

Observation
  Pod demo-crashloop is in CrashLoopBackOff with 317 restarts.
  Container exits with code 1 immediately after printing "starting".
  BackOff event has fired 4836 times.

Root Cause
  The container application exits with a non-zero exit code (1) on startup,
  indicating the process is crashing before it can run successfully.

Remediation
  1. Inspect the container entrypoint / command for startup errors
  2. Check if required env vars or config files are missing
  3. kubectl describe pod demo-crashloop -n kubefriend-test
  4. kubectl logs demo-crashloop -n kubefriend-test --previous

Prevention
  Add liveness and readiness probes to detect crashes early.
  Set resource limits to prevent OOM-triggered exits.

Total time: ~12 seconds from question to complete answer. Three K8s API calls, zero manual kubectl commands.
