Episode 2 — System Design: Architecture of an AI DevOps Tool

⏱ Suggested length: 15–18 min
Architecture System Design Design Decisions No code
Video AI Prompt
TITLE: kubefriend EP2 — System Design: Architecture of an AI DevOps Tool HOOK (0:00–0:30): "Before writing a single line of code, we designed the full system. In this episode I'll walk you through every architectural decision — what we built, how it fits together, and why we made each choice over the alternatives." SCRIPT (0:30–14:00): Section 1 — The Full Architecture Diagram (3 min) Show the complete architecture: Browser → React frontend → FastAPI backend → LangGraph Agent → 7 Kubernetes tools → Kubernetes cluster. Also show the LLM providers (OpenAI, watsonx, Ollama) connecting into the agent. Walk through the data flow for a single question from start to finish. Section 2 — Why FastAPI? (2 min) Explain why FastAPI was chosen for the backend: async-native Python, built-in SSE support for streaming, automatic API documentation, and the fact that Python is the standard language for LLM tooling. Compare briefly to alternatives: Flask (no async), Node.js Express (different language ecosystem from LLM libs). Section 3 — Why native process, not Docker? (2 min) Explain the oc login tunnel problem. When you run oc login to connect to OpenShift or IBM ROKS, the cluster API is tunnelled to localhost on your Mac. A Docker container has its own localhost — it cannot reach the Mac's localhost where the tunnel is. A native Python process running on Mac shares the same network as the tunnel. This is a real infrastructure constraint, not a preference. Section 4 — Why SSE for streaming? (2 min) Contrast WebSocket vs SSE. SSE is unidirectional server-to-client, which is exactly what we need: the agent is working and pushing updates to the browser. SSE is simpler, works over plain HTTP, and is natively supported by browsers. No library needed on the client — just the browser's built-in EventSource API. Section 5 — The three LLM providers (2 min) Explain why kubefriend supports OpenAI, IBM watsonx, and Ollama. OpenAI for best quality. watsonx for IBM Cloud enterprise deployments where data must stay on IBM infrastructure. Ollama for completely offline, zero-cost, private use. The LangChain abstraction means switching between them is a single environment variable. Section 6 — Key design principles (1 min) Three principles that guided every decision: (1) grounded answers — always call a real tool, never guess, (2) lazy initialisation — don't crash the server just because one component has a config issue, (3) extensibility — adding a new tool or a new LLM provider should require changing the minimum number of files. VISUALS: - Full architecture diagram (animated, build it up layer by layer) - Docker localhost vs Mac localhost diagram - SSE vs WebSocket comparison slide - Three LLM provider cards with logos - Design principles as three cards CLOSING (14:00–15:30): "Now we know what we're building and why every piece is there. In the next episode we'll meet LangChain — the library that lets us talk to any LLM with the same code."
Key Talking Points for Presenter
  • Architecture walkthrough: browser → FastAPI → LangGraph → tools → cluster
  • The oc login tunnel problem — why Docker breaks it, why native doesn't
  • SSE vs WebSocket — why SSE is the right choice for one-way streaming
  • Why three LLM providers: quality (OpenAI) vs enterprise (watsonx) vs offline (Ollama)
  • The LangChain abstraction: one interface, any LLM behind it
  • Lazy LLM init — the server shouldn't crash if your LLM key is wrong

Episode 3 — LangChain: The LLM Abstraction Layer

⏱ Suggested length: 18–20 min
LangChain LLM Integration Code Walkthrough factory.py
Video AI Prompt
TITLE: kubefriend EP3 — LangChain: One Interface to Rule All LLMs HOOK (0:00–0:30): "Every LLM has a different SDK, a different API, a different way to send messages. LangChain solves that with one unified interface. Let me show you how kubefriend uses it and why it matters." SCRIPT (0:30–17:00): Section 1 — The Problem Without LangChain (3 min) Show code snippets of calling OpenAI directly, calling watsonx directly, and calling Ollama directly. Each one looks completely different — different class names, different method names, different response shapes. Point out: if you want to switch LLMs, you have to rewrite all of this. Now show the LangChain version: one method, same call, same response format, regardless of provider. Section 2 — What is BaseChatModel? (3 min) Introduce BaseChatModel as the central interface. Explain: .invoke() sends messages and gets a response, .bind_tools() attaches tool schemas so the LLM knows what it can call, .astream_events() runs asynchronously and yields events as tokens are produced. Every LangChain LLM implements this interface. Our code only ever calls these three methods. Section 3 — The Message Types (3 min) Walk through the four message types: SystemMessage (the rules for the LLM), HumanMessage (the user's question), AIMessage (the LLM's reply — either a tool call or text), ToolMessage (the result a tool returned). Show how a full conversation is just a list of these four types growing over time. Draw the message sequence on screen. Section 4 — The @tool Decorator (3 min) Show the get_pod_status function. Before the decorator it's just a Python function. After @tool, LangChain has read its name, docstring, and type hints and built a structured schema from them. That schema is what gets sent to the LLM so it knows the function exists and how to call it. Emphasise: the docstring IS the tool description the LLM reads. Write it clearly or the LLM won't use the tool correctly. Section 5 — factory.py code walkthrough (3 min) Open factory.py. Walk through the get_llm() function. Show how LLM_PROVIDER env var controls which branch runs. Show the ChatOpenAI, ChatWatsonx, and ChatOllama instantiation. Show that the return type is always BaseChatModel. Explain lazy initialisation: the LLM is not built at import time — it's built when the first chat request arrives. This means a bad API key doesn't crash the server on startup. VISUALS: - Split screen: OpenAI SDK vs watsonx SDK vs LangChain (same call) - BaseChatModel interface diagram with .invoke(), .bind_tools(), .astream_events() - Message sequence diagram: System → Human → AI(tool_call) → Tool → AI(answer) - factory.py code shown with annotations - @tool decorator before/after with schema output shown CLOSING (17:00–18:30): "LangChain gives us the vocabulary — messages, tools, a uniform LLM interface. But it doesn't run the agent loop. That's LangGraph's job. Next episode we'll build the ReAct reasoning engine."
Key Talking Points for Presenter
  • The problem: every LLM SDK looks different — LangChain gives a single interface
  • BaseChatModel: .invoke(), .bind_tools(), .astream_events() — three methods, that's it
  • Four message types and the conversation as a growing list
  • @tool decorator: turns a Python function into a structured LLM-callable tool
  • The docstring is what the LLM reads — it matters more than you think
  • factory.py: get_llm() returns BaseChatModel regardless of provider
  • Lazy init: don't build the LLM at import time — defer to first request

Episode 4 — LangGraph & ReAct: Building the Agent Brain

⏱ Suggested length: 20–22 min
LangGraph ReAct Pattern Code Walkthrough graph.py state.py
Video AI Prompt
TITLE: kubefriend EP4 — LangGraph and ReAct: Building the AI Reasoning Loop HOOK (0:00–0:30): "A chatbot answers questions. An agent takes actions. The difference is a reasoning loop — think, act, observe, think again. In this episode I'll show you how we built that loop using LangGraph, and why it makes kubefriend far more powerful than any chatbot." SCRIPT (0:30–19:00): Section 1 — What is ReAct? (3 min) Explain the ReAct pattern: Reasoning + Acting. The LLM thinks about what to do next, takes an action (calls a tool), observes the result, thinks again based on the new information, and repeats until it has enough to answer. Contrast this with a simple chatbot that responds from training data in one shot. Show the loop visually. Section 2 — Why LangGraph? (3 min) Show what a naive while loop implementation looks like. Point out the problems: no streaming, no checkpointing, no parallel tool calls, no observability. LangGraph models the agent as a compiled, validated graph. Errors surface at startup, not mid-conversation. Async streaming is built in. The graph is inspectable and debuggable. Section 3 — Core Concepts: State, Nodes, Edges (4 min) Explain each concept with the kubefriend implementation. State is AgentState — a TypedDict holding the growing message list. The add_messages reducer means nodes append to the list rather than replacing it. Two nodes: the agent node (LLM thinks) and the ToolNode (executes tool calls). Two edge types: an unconditional edge from tools back to agent, and a conditional edge from agent that routes to tools or END based on whether the LLM made a tool call. Section 4 — should_continue() — the routing function (2 min) Show the should_continue function. It reads the last message in state. If the AIMessage has tool_calls, route to the tools node. If it has content and no tool_calls, the LLM is done — route to END. Emphasise: the LLM itself decides when it has enough data to stop. We don't hard-code "call exactly 3 tools". Section 5 — graph.py code walkthrough (4 min) Walk through every line of graph.py. StateGraph construction, add_node calls, add_edge and add_conditional_edges, compile(). Show how compile() validates the graph. Show the singleton pattern: agent_graph is built once at startup and reused for all requests. Show how _get_llm_with_tools() is lazy — first call builds and caches, subsequent calls return the cache. Section 6 — Live trace of a real question (3 min) Walk through what happens step-by-step when a user asks "Why is my demo-crashloop pod failing?". Show the message list growing: System → Human → AI(get_pod_status) → Tool(result) → AI(get_pod_logs) → Tool(result) → AI(get_pod_events) → Tool(result) → AI(final answer). Show how should_continue routes after each step. VISUALS: - ReAct loop animation: Think → Act → Observe → Think - Naive while loop code vs LangGraph graph code side by side - Graph diagram: START → agent → [tools → agent] → END - AgentState message list growing animation - graph.py code with live annotations - Message sequence trace for the demo-crashloop question CLOSING (19:00–20:30): "We have the brain. Now we need the hands — the Kubernetes tools the agent can call to read your cluster. Next episode we'll build all seven of them."
Key Talking Points for Presenter
  • ReAct = Reasoning + Acting — think, call tool, observe result, repeat
  • A while loop works but breaks at scale — LangGraph gives compile-time validation, async, streaming
  • State = growing message list; add_messages reducer appends, not replaces
  • Two nodes: agent (LLM) and ToolNode (executes tool calls automatically)
  • should_continue() — the LLM decides when to stop, not hard-coded logic
  • compile() validates the graph at startup — runtime errors are caught early
  • Lazy LLM cache — built on first request, reset when provider is switched

Episode 5 — The 7 Kubernetes Tools: Giving the Agent Eyes

⏱ Suggested length: 20–22 min
Kubernetes Tools Code Walkthrough tools/ k8s_client.py
Video AI Prompt
TITLE: kubefriend EP5 — The 7 Kubernetes Tools: Giving the Agent Eyes into Your Cluster HOOK (0:00–0:30): "The agent is only as good as the data it can see. In this episode we build the seven tools that give kubefriend direct, live access to your Kubernetes cluster — and we'll see exactly how the LLM decides which one to call and when." SCRIPT (0:30–19:00): Section 1 — k8s_client.py: the shared Kubernetes connection (3 min) Open k8s_client.py. Explain that the Kubernetes Python SDK reads ~/.kube/config — the same file kubectl uses. Walk through the load order: try in-cluster config first (for when kubefriend itself runs inside Kubernetes), fall back to kubeconfig file. Explain os.path.expanduser() for tilde paths. Explain why the client is loaded once at module import time: it creates a singleton configuration that all tools share. Section 2 — How @tool docstrings become LLM instructions (2 min) Show get_pod_status with its docstring. Explain the exact mechanism: when .bind_tools(TOOLS) is called, LangChain reads each tool's name, docstring, and type hints and builds a JSON schema. That schema is injected into every LLM request. The LLM reads these descriptions and decides which tool to call based on the user's question. The docstring IS the tool's API contract with the LLM. Section 3 — get_pod_status (2 min) Walk through what it returns: pod phase, container states, restart count, last termination reason (OOMKilled, Error), pod conditions. Explain why "last termination reason" is critical — it tells you not what is happening now but what happened before the latest restart. Section 4 — get_pod_logs and get_pod_events (2 min) Explain when the agent uses each: logs when there are restarts and we need to see the application error; events when the pod is Pending or status is unclear (events show Kubernetes scheduler decisions, image pull errors, and backoff warnings). Section 5 — get_deployment and get_pvc (2 min) Deployment tool returns desired/ready/available replica counts, rollout conditions, and image versions — useful when the problem is a stalled rollout, not a single pod. PVC tool checks if storage is Bound, Pending, or Lost — a very common cause of pods stuck in Pending state. Section 6 — find_unused_pods (2 min) Explain evicted, Succeeded, Failed, Unknown pods and why they accumulate silently. Show how this tool identifies pods safe to delete, with configurable thresholds for age and restart count. Section 7 — get_crd_resources: the generic CRD tool (4 min) This is the most sophisticated tool. Explain CRDs (Custom Resource Definitions) — any team can extend Kubernetes with their own resource types. IBM watsonx uses a "workloads" CRD. OpenSearch, Milvus, Presto each have their own. Rather than writing a separate tool for each, get_crd_resources auto-discovers any CRD by querying the ApiextensionsV1Api, finding the correct group and version, then querying the resource. Supports filtering by type, state, name, namespace. Works for any CRD in any cluster. Section 8 — registry.py: the single source of truth (1 min) Show the file. It imports all seven tools and exports them as a TOOLS list. Adding a new tool = one import line + one entry in the list. No other files need to change. VISUALS: - ~/.kube/config content shown annotated - @tool schema generation diagram (docstring → JSON schema → LLM request) - Each tool shown with its real output from the demo-crashloop test - CRD auto-discovery flow diagram - registry.py shown — simplicity of the file makes the point CLOSING (19:00–20:30): "Seven tools, one registry, and the LLM knows how to use all of them. Next episode we connect this to the outside world: the FastAPI backend and the SSE streaming that makes it all feel instant."
Key Talking Points for Presenter
  • k8s_client.py loads once — all tools share the same connection singleton
  • @tool docstring = what the LLM reads to decide when to call it — write it carefully
  • get_pod_status: last termination reason tells you why it died before, not just current state
  • Logs vs events: logs = app error; events = Kubernetes scheduler/infrastructure error
  • PVC Pending is a silent but very common cause of pods never starting
  • get_crd_resources: auto-discovers any CRD — one generic tool covers workloads, OpenSearch, Kafka, anything
  • registry.py: adding a tool = two lines, nothing else changes

Episode 6 — FastAPI & SSE: Streaming the Agent to the Browser

⏱ Suggested length: 18–20 min
FastAPI SSE Streaming Code Walkthrough main.py dashboard.py
Video AI Prompt
TITLE: kubefriend EP6 — FastAPI and SSE: How We Stream the Agent to the Browser in Real Time HOOK (0:00–0:30): "You've seen the agent reason step by step. But how does that get to the browser in real time, token by token? This episode is about the plumbing — FastAPI, Server-Sent Events, and conversation memory." SCRIPT (0:30–17:00): Section 1 — What is SSE and why not WebSocket? (3 min) Explain SSE: a simple HTTP connection that stays open. The server pushes events to the browser as they happen. The browser uses the built-in EventSource API — no library needed. Contrast with WebSocket: bidirectional, more complex, better for chat apps where the client also sends many messages. For kubefriend, the client sends one message and the server streams back a long response — SSE is the perfect fit. Section 2 — The SSE event format (2 min) Show the wire format: data: {"type": "token", "data": "Why"}\n\n. Every event is a JSON object with a type field (token, tool_call, tool_result, done, error) and a data payload. The frontend switches on the type to decide what to do with each event. Section 3 — main.py: the /api/chat endpoint (4 min) Open main.py. Show the POST /api/chat endpoint returning EventSourceResponse wrapping the _stream_agent async generator. Walk through _stream_agent: it looks up conversation history, appends the new user message, calls agent_graph.astream_events(), and maps LangGraph events to SSE events. Show each mapping: on_chat_model_stream → token (only for non-tool-call chunks), on_tool_start → tool_call, on_tool_end → tool_result, on_chain_end(LangGraph) → captures final messages for conversation store. Section 4 — Conversation memory (2 min) Explain conversation_store: a dict from conversation_id to list of past messages. On each request, the history is prepended to the new message before sending to the agent. This enables multi-turn context: "What about the other pod?" works because the agent still has the previous messages in its context. Section 5 — /api/dashboard: the live dashboard endpoint (2 min) Explain build_dashboard: it lists all pods in the namespace, classifies them as healthy/warning/critical, and for unhealthy pods runs a quick AI diagnosis concurrently. The frontend polls this endpoint every 30 seconds to keep the dashboard live. Section 6 — /api/llm/reset: hot-swap without restart (2 min) Show the LLM management endpoints. POST /api/llm/reset?provider=watsonx calls reset_llm_cache() which sets the global cache to None. The next chat request rebuilds the LLM with the new provider. No server restart needed — used by ./kubefriend llm watsonx. VISUALS: - SSE vs WebSocket comparison diagram - SSE wire format shown in browser DevTools Network tab - main.py annotated with event flow arrows - Conversation store diagram: conversation_id → [messages] - LangGraph event → SSE event mapping table CLOSING (17:00–18:30): "The backend is complete. Next episode we build the frontend — the React UI that consumes these SSE events and turns them into a streaming chat experience with a live tool call panel."
Key Talking Points for Presenter
  • SSE vs WebSocket: SSE is simpler, unidirectional, perfect for one-response streaming
  • SSE wire format: data: {json}\n\n — the browser's EventSource handles the rest
  • LangGraph event → SSE event mapping: the translation layer between agent internals and browser
  • Only stream non-tool-call tokens — tool call chunks look like tokens but shouldn't be shown as text
  • conversation_store enables multi-turn: history is prepended on every request
  • /api/llm/reset clears the LLM cache — hot-swap without restart
