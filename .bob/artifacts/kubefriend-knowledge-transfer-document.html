1. What is kubefriend? — The Problem It Solves

Debugging a failing Kubernetes pod typically requires a developer to run 4–6 commands, read and correlate their outputs, and then reason about what went wrong:

kubectl get pod openrag-backend -n prod
kubectl describe pod openrag-backend -n prod
kubectl logs openrag-backend -n prod --previous
kubectl get events -n prod --field-selector involvedObject.name=openrag-backend

This is mechanical, repetitive, and requires K8s expertise. kubefriend replaces this entire workflow with a single natural-language question:

💬 "Why is my openrag-backend pod failing?"

The assistant automatically calls the right tools, reads the data, correlates it, identifies the root cause, and streams back a structured explanation with exact kubectl remediation commands.

Who it's for

  • Developers who own services but aren't Kubernetes experts
  • Platform engineers who want faster incident triage
  • SREs doing on-call — check dashboard, ask AI, fix fast
  • IBM Cloud / ROKS teams — includes CRD support for watsonx workloads, OpenSearch, Milvus, Presto

4. What is LangChain? — The LLM Abstraction Layer

LangChain is an open-source Python library that provides a uniform interface for working with any Large Language Model — regardless of which provider it comes from.

The problem LangChain solves

Every LLM provider has a different SDK, a different API shape, and a different way to send messages:

# Without LangChain — different code for every LLM

# OpenAI
client = openai.OpenAI()
response = client.chat.completions.create(model="gpt-4o", messages=[...])
text = response.choices[0].message.content

# IBM watsonx
model = ModelInference(model_id="llama-3-3-70b", credentials=..., project_id=...)
response = model.chat(messages=[...])
text = response["choices"][0]["message"]["content"]

# Ollama
client = ollama.Client()
response = client.chat(model="llama3", messages=[...])
text = response["message"]["content"]

With LangChain, all three look identical:

# With LangChain — same code regardless of LLM
from langchain_core.messages import HumanMessage

response = llm.invoke([HumanMessage(content="Why is my pod failing?")])
text = response.content  # always the same, no matter which LLM

The key abstraction: BaseChatModel

Every LLM in LangChain implements the BaseChatModel interface. It defines three methods that every provider must support:

MethodWhat it doesUsed in kubefriend
.invoke(messages)Send messages, get one response backAgent node calling the LLM each loop iteration
.bind_tools(tools)Attach a list of tools the LLM can callCalled once at startup — tells LLM about our 7 K8s tools
.astream_events()Run async and stream back events as they happenSSE token streaming to the browser

How LangChain is used in kubefriend

factory.py — build any LLM with one function
# get_llm() returns a BaseChatModel — the rest of the code never
# knows or cares whether it's OpenAI, watsonx, or Ollama
def get_llm() -> BaseChatModel:
    provider = os.getenv("LLM_PROVIDER", "openai")
    if provider == "openai":    return ChatOpenAI(model="gpt-4o", ...)
    if provider == "watsonx":   return ChatWatsonx(model_id="llama-3-3-70b", ...)
    if provider == "ollama":    return ChatOllama(model="llama3", ...)
graph.py — bind tools to the LLM
# .bind_tools() sends tool schemas to the LLM so it knows what's available
# Returns a new LLM object that includes tool definitions in every request
llm_with_tools = get_llm().bind_tools(TOOLS)
tools/ — @tool decorator
# @tool turns a plain Python function into a LangChain Tool object
# LangChain reads the docstring + type hints to build the schema
# that gets sent to the LLM so it knows how to call this function
@tool
def get_pod_status(namespace: str, pod_name: str) -> str:
    """Get the current status of a Kubernetes pod. Use this when..."""
    ...

LangChain message types

Every piece of conversation in kubefriend is a LangChain message object:

Message TypeWho creates itWhat it contains
SystemMessagekubefriend (hardcoded)The system prompt — rules the LLM must follow
HumanMessageThe userThe question: "Why is my pod failing?"
AIMessageThe LLMEither a tool call request OR the final text answer
ToolMessageLangGraph ToolNodeThe result returned by a tool (e.g. pod status output)
In summary: LangChain is the vocabulary kubefriend uses to talk to LLMs — message types, tool schemas, the BaseChatModel interface. It doesn't run the agent loop. That's LangGraph's job.

5. What is LangGraph? — The Agent Orchestration Framework

LangGraph is a library built on top of LangChain that lets you define an AI agent as a directed graph of nodes and edges. It handles the loop, the state, and the routing logic.

Why not just call the LLM in a while loop?

You could write this manually:

# Naive approach — while loop
messages = [system_prompt, user_message]
while True:
    response = llm.invoke(messages)
    messages.append(response)
    if response.tool_calls:
        result = run_tool(response.tool_calls[0])
        messages.append(ToolMessage(result))
    else:
        break  # done

This works for simple cases, but breaks quickly when you need:

  • Async streaming (yield tokens as they come)
  • Multiple parallel tool calls
  • Checkpointing / resuming a conversation
  • Complex branching (different paths based on state)
  • Observability — seeing which node ran, with what input/output

LangGraph solves all of these by modelling the agent as a graph that can be compiled, validated, streamed, and inspected.

Core concepts

ConceptWhat it isIn kubefriend
StateA typed dictionary that every node reads from and writes to. Persists across the entire loop.AgentState — holds the growing list of messages
NodeA Python function that takes State in, returns a partial State update out.agent_node (LLM thinks) and ToolNode (executes tools)
EdgeA connection from one node to another — defines what runs next.tools → agent (always loop back after tool call)
Conditional EdgeAn edge whose destination is decided by a function at runtime.agent → tools OR agent → END based on whether LLM made a tool call
ReducerA function that says how to merge a node's output into State.add_messages — appends new messages rather than replacing the list
Compiled graphThe result of builder.compile() — a validated, runnable object.agent_graph — built once at startup, reused for every chat request

How LangGraph validates the graph at compile time

When you call builder.compile(), LangGraph checks:

  • Every node that is referenced in an edge actually exists
  • The should_continue function only returns node names that exist ("tools" or "__end__")
  • There are no cycles that can't be reached

Errors are caught at startup, not during a live chat — so misconfigured graphs fail fast.

How LangGraph handles streaming

agent_graph.astream_events() is an async generator that fires events as the graph executes:

Event nameWhen it fireskubefriend uses it to
on_chat_model_streamEvery token the LLM producesStream token to browser via SSE
on_tool_startA tool is about to be calledShow "calling get_pod_status…" in Tool Panel
on_tool_endA tool has returned its resultShow tool result in Tool Panel
on_chain_end (LangGraph)The full graph has finishedSave full message history for next turn
In summary: LangGraph is the engine that drives the agent loop — it decides when to call the LLM, when to call a tool, when to stop, and how to stream events to the outside world. LangChain provides the building blocks (messages, tools, LLM interface) that LangGraph orchestrates.

6. The ReAct Flow — How kubefriend Reasons Step by Step

ReAct = Reasoning + Acting. It is a prompting pattern where the LLM alternates between thinking about what to do next and taking an action (calling a tool). The result of each action feeds back into the next round of thinking.

ReAct vs. a simple chatbot

Simple chatbotkubefriend (ReAct agent)
Knows about your cluster?No — answers from training data onlyYes — calls live Kubernetes APIs
AccuracyHallucinated answersGrounded in real cluster data
Multi-step reasoningNo — one responseYes — loops until it has enough data
Can run commands?NoYes — calls 7 K8s tools

What is in AgentState at the end?

After the loop completes, the full message history in AgentState looks like this:

messages = [
  SystemMessage("You are kubefriend, a K8s expert..."),
  HumanMessage("Why is my demo-crashloop pod failing?"),
  AIMessage(tool_calls=[{"name": "get_pod_status", "args": {...}}]),
  ToolMessage("317 restarts, CrashLoopBackOff, exit=1"),
  AIMessage(tool_calls=[{"name": "get_pod_logs",   "args": {...}}]),
  ToolMessage("starting\n[exited]"),
  AIMessage(tool_calls=[{"name": "get_pod_events", "args": {...}}]),
  ToolMessage("BackOff x4836"),
  AIMessage(content="**Observation**\nPod is in CrashLoopBackOff..."),
]

This entire list is stored in conversation_store[conversation_id] and sent back to the LLM on the next user question — enabling multi-turn context-aware conversations.

The routing decision — should_continue()

After every agent node, LangGraph calls this function to decide where to go next:

def should_continue(state: AgentState) -> Literal["tools", "__end__"]:
    last_message = state["messages"][-1]   # what did the LLM just return?

    if last_message.tool_calls:            # LLM wants to call a tool
        return "tools"                    # → route to ToolNode

    return END                             # LLM wrote text answer → stop
Key insight: The LLM itself decides when it has enough information to stop. kubefriend doesn't hard-code "call exactly 3 tools". The LLM may call 1 tool for a simple question or 5 tools for a complex one — it stops when it feels confident enough to answer.

7. The Agent Reasoning Loop — Code Deep Dive

How the three files wire together

state.py — the agent's memory
class AgentState(TypedDict):
    messages: Annotated[list[BaseMessage], add_messages]
    #                                         ↑
    # add_messages is a reducer: when a node returns
    # {"messages": [new_msg]}, it APPENDS — not replaces
graph.py — the two nodes and the routing
# Node 1 — LLM thinks
def agent_node(state):
    messages = state["messages"]
    if not isinstance(messages[0], SystemMessage):
        messages = [SystemMessage(SYSTEM_PROMPT)] + list(messages)
    response = _get_llm_with_tools().invoke(messages)   # call LLM
    return {"messages": [response]}                    # append to state

# Node 2 — tool executor (LangGraph built-in)
_tools_node = ToolNode(TOOLS)
# ToolNode reads tool_calls from last AIMessage,
# calls the matching Python function, wraps result in ToolMessage

# Wire the graph
builder = StateGraph(AgentState)
builder.add_node("agent", agent_node)
builder.add_node("tools", _tools_node)
builder.add_edge(START, "agent")
builder.add_conditional_edges("agent", should_continue)  # tools or END
builder.add_edge("tools", "agent")                       # always loop back
agent_graph = builder.compile()
main.py — streaming the graph to the browser
async for event in agent_graph.astream_events(
    {"messages": history + [HumanMessage(user_question)]},
    version="v2",
):
    if event["event"] == "on_chat_model_stream":
        yield _sse_event("token", chunk.content)   # → browser
    elif event["event"] == "on_tool_start":
        yield _sse_event("tool_call", ...)          # → Tool Panel
    elif event["event"] == "on_tool_end":
        yield _sse_event("tool_result", ...)        # → Tool Panel

8. The 7 Kubernetes Tools

Each tool is a Python function decorated with @tool. LangChain reads the docstring to build the description the LLM uses to decide when and how to call it.

ToolWhat it fetchesWhen the agent uses it
get_pod_statusPhase, container states, restart count, last termination reason (OOMKilled, Error), pod conditionsFirst tool called — establishes the baseline state
get_pod_logsLast N lines of container stdout/stderr (default 100)After seeing CrashLoopBackOff — logs reveal the application error
get_pod_eventsKubernetes events: scheduling failures, image pull errors, BackOff warningsWhen pod is Pending or status is unclear
get_deploymentReplica counts (desired/ready/available), rollout conditions, image versions, strategyWhen the problem may be at deployment level
get_pvcPVC names, status (Bound/Pending/Lost), capacity, storage classWhen a pod is stuck Pending — may be waiting for a PVC
find_unused_podsEvicted, Succeeded, Failed, Unknown podsCleanup queries: "what pods are safe to delete?"
get_crd_resourcesAny Custom Resource Definition — auto-discovers group/versionIBM watsonx workloads, OpenSearch, Milvus, Presto, or any CRD

10. How watsonx Was Debugged & Made to Work

The error

403 project_id 4be90509-... is not associated with a WML instance

Root cause

The watsonx project existed in IBM Cloud, but had no Watson Machine Learning (WML) service instance associated with it.

Fix

  1. Open dataplatform.cloud.ibm.com → select the project
  2. Go to Manage → Services & integrations → Associate service
  3. Select or create a Watson Machine Learning instance

Model selection

The configured model (ibm/granite-3-8b-instruct) was not available on this WML instance. We listed all 17 available models and picked meta-llama/llama-3-3-70b-instruct — full tool-calling support, best reasoning quality in the list.

Resilience fix

LLM initialisation was moved from module import time to first chat request (lazy init). Now the server starts and serves health checks and the dashboard even if LLM credentials are temporarily broken.
